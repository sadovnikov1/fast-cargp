# План архитектурной трансформации Fast Cargo

Подготовлено к защите перед архитектурным штабом холдинга «Плюс Ритейл». Горизонт: 12 месяцев до демонтажа монолита, контрольная точка — 3 месяца (аналитика в реальном времени для DWH холдинга).

## 1. Выгоды бизнеса

- **Масштаб без пересборки штата.** Независимые домены (заказы, склад, доставка, финансы, платежи, телематика) снимают барьер для десятикратного роста объёма (до 500 тыс. отправлений/сутки) — условие сделки.
- **Соответствие требованиям холдинга как условие сделки.** 152-ФЗ, PCI DSS и TOGAF-совместимость — без этого интеграция CRM и платёжных сценариев холдинга юридически невозможна.
- **Меньше простоев операционного ядра.** 99,95% доступности и 0% потерь платёжных вебхуков — меньше упущенной выручки и штрафов за задержку отгрузок.
- **Видимый результат на 3-м месяце.** DWH-аналитика с задержкой ≤5 сек без переписывания легаси — ранний низкорисковый win, укрепляющий доверие холдинга до начала тяжёлой части программы.

## 2. Базовая и целевая архитектура

**AS-IS.** Монолитный бэкенд с единой кодовой базой BFF на веб и мобильное приложение, шлюз (FastAPI) синхронно проксирует весь трафик на монолит, все домены (Заказы, Warehouse, Доставка, Финансы) пишут в один физический инстанс PostgreSQL с жёсткими FK-связями. **Главный антипаттерн — Shared Database + синхронный Big Ball of Mud**: тяжёлые отчёты «Финансов» блокируют транзакционные таблицы и останавливают создание заказов и запись GPS; рост нагрузки на СУБД исчерпывает воркеры шлюза, он падает по таймауту (504) и теряет вебхуки платежей.

**TO-BE.** Событийно-ориентированная микросервисная архитектура, **Database-per-Service**, домены изолированы (Orders, Warehouse, Delivery, Finance + новые: Payments, Customer Profile, Telematics Ingestion, EDI Gateway). Паттерны: шина событий вместо синхронных in-process вызовов; **Saga с компенсациями** для цепочки EDI ORDERS → DESADV → INVOIC вместо распределённых блокировок и cross-domain JOIN; **CDC по WAL** для вывода данных во внешние контуры без доступа к транзакционной базе; **Strangler Fig** для поэтапного выноса доменов без остановки сервиса; API Gateway/BFF, разделённый по каналам, вместо единого BFF, который сегодня роняет мобильное API при правках веба.

## 3. Область применения

**In-scope:** домены Orders/Warehouse/Delivery/Finance (поэтапный вынос по Strangler Fig); CDC-контур для аналитики холдинга; изолированный Payments-модуль (редирект/виджет эквайера, без PAN в контуре Fast Cargo); сервис Customer Profile для ПДн (152-ФЗ); EDI-шлюз (ORDERS/DESADV/INVOIC); ingestion-контур телематики IoT; событийная шина; разделение API Gateway/BFF по каналам.

**Out-of-scope:** внутренние системы холдинга (CRM, DWH, корпоративная шина) — Fast Cargo подключается по контракту/API, не меняет их архитектуру; выбор конкретного банка-эквайера — коммерческое решение холдинга; переписывание бизнес-логики модулей монолита на 3-месячном этапе (только 12-месячный горизонт); справочники master_data (ФИАС, тарифы) — не являются источником проблем по аудиту.

## 4. Ограничения и допущения

- Срок: 12 месяцев до полного демонтажа монолита; веха — 3 месяца на DWH-аналитику без изменения кода монолита и без SQL-нагрузки на его базу.
- ИБ: 152-ФЗ (изоляция и обезличивание ПДн), ГОСТ Р, PCI DSS для платёжного контура — жёсткие рамки, не предмет обсуждения.
- Бюджет и конкретные показатели утилизации ЦОД в кейсе не заданы — **допущение**: первый транш бюджета покрывает 3-месячный MVP (CDC + брокер сообщений), остальное утверждается поэтапно по вехам дорожной карты совместно с производственно-инфраструктурным департаментом холдинга.
- По итогам аудита текущая ИТ-команда Fast Cargo ориентирована на эксплуатацию, не на архитектурную трансформацию — **допущение**: для событийно-ориентированных компетенций (Kafka/CDC/DevOps) потребуется усиление извне или от холдинга; без этого сроки 12-месячного этапа под риском.

## 5. Transition Architecture (горизонт 3 месяца)

| Уровень | AS-IS | Переходное состояние (3 мес.) | Разрыв (gap) и локация |
|---|---|---|---|
| **Данные (Data)** | Аналитические данные недоступны холдингу иначе как через прямые SELECT-запросы к операционной БД PostgreSQL. | Данные о статусах заказов вычитываются асинхронно из WAL-журнала PostgreSQL (логическая репликация) и публикуются в топик брокера сообщений — без единого запроса к транзакционным таблицам. | Разрыв — нет выделенного контура аналитики и CDC-потока. Локация — слой хранения: включение `wal_level=logical`, replication slot, CDC-коннектор (Debezium). |
| **Приложения (Apps)** | BFF обслуживает веб и мобильное приложение единой кодовой базой (правки веба ломают мобильное API); интеграционный шлюз синхронно ждёт ответ монолита и падает по 504 при нагрузке, теряя вебхуки. | BFF и шлюз **не меняются** — требование запрета правок легаси соблюдено буквально. Добавляется новый, полностью автономный компонент — CDC-publisher (Kafka Connect), не входящий в кодовую базу монолита и не вызывающий его API. | Разрыв — нет отдельного сервиса публикации событий вне монолита. Локация — middleware-слой: новый изолированный компонент, не затрагивающий BFF/FastAPI-шлюз. |
| **Инфраструктура (Infra)** | Один физический инстанс PostgreSQL несёт всю OLTP-нагрузку; выделенных ресурсов под стриминг или аналитику нет; фактическая утилизация ЦОД не оценена (требует входных данных от производственно-инфраструктурного департамента). | Логическая репликация включена на существующем инстансе (конфигурация СУБД, не код); брокер сообщений (Kafka/Redpanda) и Kafka Connect развёрнуты в отдельном, изолированном от прода контуре с собственным бюджетом CPU/памяти. | Разрыв — нет инфраструктуры брокера сообщений и мониторинга лага replication slot. Локация — инфраструктурный слой: новый отдельный контур + алертинг на рост WAL. |

## 6. Описание переходного состояния — CDC по WAL-логам

Паттерн: **Change Data Capture через логическую репликацию PostgreSQL** (Debezium/Kafka Connect поверх `wal_level=logical`). PostgreSQL и так непрерывно пишет WAL для собственной отказоустойчивости; логическая репликация декодирует этот уже существующий поток в структурированные события изменений строк — это процесс уровня СУБД, параллельный транзакционному пути, а не ещё один клиент, конкурирующий за блокировки. Отсюда три свойства, закрывающие требование вехи буквально: **ноль изменений кода монолита** (единственное действие — параметр СУБД, применяемый один раз в окно обслуживания); **ноль дополнительной SQL-нагрузки** (источник для DWH — WAL-поток, а не SELECT к операционным таблицам); **задержка в пределах секунд** (события публикуются в брокер сразу после коммита, доставка до DWH укладывается в ≤5 сек).

Деградация склада или биллинга (Критерий 1) не теряет геоданные и не замедляет создание заказов: WAL-поток не зависит от состояния доменных сервисов, а при остановке DWH-консьюмера лаг копится в брокере/slot, не блокируя запись в оперативную базу (риски — п. 7).

## 7. Дорожная карта, риски и план перехода

**Пакеты работ и сроки**
- Недели 1–2: включение `wal_level=logical` и replication slot на проде в окно обслуживания — инженер эксплуатации Fast Cargo.
- Недели 2–6: развёртывание изолированного контура Kafka Connect + Debezium-коннектор, фильтрация нужных таблиц (orders, waybills, invoices) — группа разработки совместно с архитектором.
- Недели 6–10: sink-консьюмер в DWH холдинга по согласованному контракту данных, нагрузочный тест, настройка мониторинга лага — совместно с аналитическим департаментом холдинга.
- Недели 10–12: пилотный прогон в проде, приёмка по критерию ≤5 сек, передача на дежурную поддержку.

**Управление рисками и план отката**
- Риск: неконсьюмируемый replication slot копит WAL на диске прода вплоть до отказа записи. Митигация — алерт на рост слота и автоматический `DROP_REPLICATION_SLOT` при превышении порога: потеря свежих аналитических данных приемлема, потеря записи в операционную базу — нет.
- Риск: логическое декодирование WAL создаёт ненулевую (хоть и существенно меньшую, чем SELECT) нагрузку CPU/IO на прод. Митигация — нагрузочный тест на staging/реплике перед включением на проде.
- План отката: при любой аномалии — `DROP_REPLICATION_SLOT` и остановка Kafka Connect. Код монолита не менялся, поэтому откат не требует редеплоя приложения — это самый дешёвый откат из всех возможных архитектурных решений.

**Критерии успешности и переключение**
- Приёмка: задержка событие → DWH ≤5 сек непрерывно на протяжении 2 недель пилота под реальной нагрузкой.
- Guardrails: 0 новых SQL-запросов к операционной базе от аналитического контура (гарантировано природой решения); 0 коммитов в репозиторий монолита за период пилота (проверяется по истории git).
- Переключение в пром: по итогам пилота — перевод DWH-консьюмера в постоянную эксплуатацию, снятие пилотного статуса, передача мониторинга лага slot дежурной команде.
